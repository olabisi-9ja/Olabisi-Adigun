What I Check Before a Site Goes Live

A concrete, opinionated launch checklist, drawn from actually applying it to this very site. No vague advice; each item is something you can verify.

Every time I ship a site I run the same checklist. Not because I enjoy checklists, but because the things that embarrass you after launch are always the small, verifiable ones. Here is the current version, with the numbers from applying it to this site.

Performance: kill the heavy things first

Performance work is 90% removing weight, not micro-optimising. On this site the two heaviest offenders were a 1.8 MB PNG screenshot and a ~600 KB third-party 3D library loaded from a CDN. Converting the image to WebP at a sensible size brought it to ~60 KB, and replacing the 3D library with a tiny canvas-2D projection removed the dependency entirely. That single change cut the JavaScript payload by an order of magnitude.

  • Compress and resize images; use WebP/AVIF and set width/height to avoid layout shift.
  • Drop or self-host third-party scripts you do not strictly need.
  • Defer non-critical JS and CSS; preload only the true critical path.

SEO: make the page describable and discoverable

  • One <title> and one meta description per page, unique across the site.
  • A canonical URL on every page, plus robots.txt, sitemap.xml and (newly) llms.txt.
  • Open Graph and Twitter card tags with a real 1200×630 image, in a format scrapers accept.
  • Structured data (JSON-LD) for the person, the site, articles and breadcrumbs.
  • A custom 404 page so dead links lead somewhere useful.

Accessibility: the cheapest wins

  • Skip-to-content link and a single <main> landmark.
  • Visible keyboard focus and full keyboard operability (the FAQ here is native <details>, so it works with no JS).
  • Contrast ratios that pass WCAG AA, in both themes.
  • Respect prefers-reduced-motion.
  • Real alt text that describes the image, not "image1".

Legal and trust

A portfolio still needs a privacy policy and terms, even if the honest privacy policy is "we store a theme preference". Saying so plainly builds more trust than a generic policy generator. Add real contact details and, if you display reviews, only real ones.

Security, even on static hosting

  • No secrets in the repo or the bundle. Static sites should have nothing to leak.
  • rel="noopener noreferrer" on every external link.
  • A published security.txt so researchers can reach you.
  • If you add CDN scripts, pin them with Subresource Integrity; better, self-host.

The final gate

Before I call anything done, I load every page in a real browser on a real (small) screen, watch the console for errors, and scroll for horizontal overflow. A clean build is not the same as a working page. If the console is quiet, the overflow is gone and the links resolve, then, and only then, is it live.

The one-line version

Remove weight, describe the page, make it usable by keyboard, be honest about data, and verify in a browser. Everything else is polish.
